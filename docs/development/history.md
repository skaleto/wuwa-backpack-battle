# 开发规范

## V134：轻量异步模式的边界

- `async_pvp.gd` 只负责协议、摘要、严格快照校验和纯匹配排序；`async_pool_client.gd` 只负责非阻塞 HTTP 与独立持久上传队列；`async_run_application.gd` 复用既有生命周期／模拟规则，增加保存优先的冻结与锁定。UI 不能自行选对手、写远端文件或因网络结果改变数值。
- `run.pvp` 与该局同文件原子保存；先冻结并持久入队，再匹配并保存对手，之后才模拟与展示。保存失败保持旧状态。`pending/locked` 期间全部整备入口冻结，包括历史合成入口；成品预览、精确合成、材料归位都通过应用提交。`matches_frozen` 在模拟前再校验己方阵容未变化。结束后重复继续不能重复发奖。
- 异步进度在原用户目录的 `async/`，不读取单机对手池，不导入手动影像。未知版本的异步存档不自动迁移到新规则池。pool 标识组合现有规则、目录摘要、模拟版本、供给、物品池与招募版本；规则改变必须发布新 pool 白名单。
- 客户端永不持有阿里云 AccessKeySecret。只存游戏身份 token；Unix 私有目录先设 `0700`，凭据最终文件 `0600`，不能先写公开临时文件再补权限。签名 URL／POST 字段不进日志、战斗历史、存档或错误提示。OSS V4 授权可含公开签名标识，但不能包含长期签名密钥。
- 补传保留原始字节，不消耗游戏 RNG，不触碰 live run。重复上传 409 必须 GET 验摘要才算成功；验证 GET 临时失败仍重试。旧身份、过期及明确不可恢复条目不阻塞新快照。上传队列有64项／7天上限；每轮网络匹配3秒、3页、4候选是小范围MVP预算，不能宣传为遍历全量大池或反作弊。
- `player/bot` 来源和补位原因必须保存到回放证据；终局保留来源，不能因清除临时状态改变归档ID而产生重复记录。网络/空池补位不伪装真人。
- 验证入口 `python3 tools/check_v134.py --jobs 2`；本地 HTTP 联调 `python3 tools/test_pvp_integration_v134.py` 明确使用测试 OSS；真实 OSS 证据另存 `docs/pvp-v134/checks/real-godot-oss.log` 与部署报告。全部QA独立存档，无系统鼠标输入；云端仅删除本次已核验摘要的测试对象，不能清理其他业务。

## V122：独立历史与版本化供给

- `supply_version` 与战斗版本分离。新局122、旧局缺省／0保持原供应和随机序列；快照、JSON归一化、练习缓存、自动匹配、恢复及手动导入都必须正确传递。玩家和练习对手使用同一供给，不偷偷改对手血量。
- 商品选择先构建合法普通分布，再施加材料稀缺和搭配权重；概率必须归一、普通零概率不得被补货凭空提高。固定真实购买／付费刷新／扩容／合成轨迹做配对测量；目标路线与无目标购买器分开报告，不能用单条路线成功率宣称全部平衡。

## 必须遵守的模块边界

1. **KISS：围绕当前完整操作划分责任。** 不为未来假设引入 ECS、全局事件总线、通用规则 DSL、平行游戏状态或大量空接口。小函数足够时不用框架；分文件不等于解耦。
2. **配方事实、资格、材料与空间分别判断。** 配方目录只接收物品类型与配方数据。材料匹配返回确切实例 UID；空间计算只负责形状、容器与落点。空间不足不能让配方关系消失。
3. **一个规则一个来源。** 旧入口只委托新实现。商店、详情、星位与战斗不得复制能力判定表；几何查询共享实现。历史存档按相应历史形状校验，不被新目录覆盖。
4. **读操作不修改游戏状态。** 查询、预览、悬停、拖动演示不能扣钱、消耗材料、推进真实 UID/随机数或写盘。未来 UID 可在隔离计划中试算，只有提交才更新计数。
5. **一次操作统一提交。** 预览与执行使用同一计划逻辑；提交前检查状态仍匹配并完整校验候选状态。失败、取消、重复确认均不产生部分扣费、丢物或重复产物。购买的挤占策略与合成不挤占、背包优先／储物后备策略分别明确保留，不能因复用代码混为一谈。
6. **展示没有写权限。** 新建或迁移的视图只接收所需值数据、绘图接口及输入事件，返回操作意图；不得接收整个 `game`、`inventory`、`run` 或改名后的泛化 context。绘图 CanvasItem 只作绘图接收者，不借它读取游戏属性。业务提交和保存不得放在视图输入/绘制函数里。
7. **动画消费结果。** 成功提交后返回独立的消耗、创建、位置数据。动画只能展示这些事实；关闭、跳过、重放都不能再次执行玩法，也不能通过共享 Dictionary 引用改真实状态。
8. **身份明确。** 物品类型、实例 UID、商品槽位、储物位置、逻辑格和屏幕坐标不得混用。商店模拟购买不能生成真实所有权；由操作/查询适配层根据真实持有状态判断，UI 不自造购买资格。
9. **过期预览不静默换料。** 确认绑定精确输入与落点；状态变化后拒绝旧请求并刷新预览。新旧接口迁移期必须识别所有旧写操作，不能仅凭覆盖不全的版本计数宣称预览仍有效。
10. **技术约束不能冒充玩法。** 新增限制须注明已确认规则或设计理由。行为调整与结构重构分开交付；不能借重构修改回合、概率、价格、效果、占格或存档规则。

- **Inventory 兼容门面**保留旧方法签名，实际操作委托上述模块，提交委托 RunSession；不再保留第二套规则。几何、实例身份、全局校验以及历史目录注入仍由此适配。操作模块可调用这些现存查询／候选清理方法，不能调用旧公开写入口形成嵌套提交。

- **CraftHandler 的 Inventory 参数**继续服务于共享校验、身份、构造、候选清理及旧材料摆放适配；纯配方、材料、空间模块不依赖 Inventory/game。后续若迁移实例与校验职责，应移走原实现，不能复制规则。

- **旧材料强化入口**维持已禁用状态；配方页购买真实商品使用统一购买计划，不能自造材料。历史存档读写、备份、迁移格式不变。
- **存储接口**沿用既有 save 契约。本次没有把内存提交与文件系统改成分布式事务，也没有新增保存重试政策；失败处理不能通过重试整次玩法操作实现。关闭窗口、导入导出后的 checkpoint 属于显式持久化请求。

## V81 同类问题排查要求

5. 保留能复现具体症状的回归，同时遍历目录中的同类物品、旋转与容器边界。报告检查范围、额外发现与已保留的设计限制，不以“测试全过”宣称所有游戏设计均正确。

本轮 `star_activation_view.gd` 仅保存真实 star_trigger 事件的双方 UID、阵营和短期显示寿命；暂停／倍速沿用反馈时钟。`PocketRules.covered_value` 为口袋预览及开场盾共用计量，不改系数。
